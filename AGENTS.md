# Contributor instructions

- Write all repository documentation, comments, examples, and diagnostics in US English.
- License original source under MPL-2.0. Preserve dependency licenses and notices, and review license compatibility before adding code or dependencies.
- Keep the LiveKit Cloud API client (`internal/livekit`) standard-library only. LiveKit's CLI (`livekit/livekit-cli`, Apache-2.0) has a client generated from the same API; it is deliberately not used: it lives in a `main`-adjacent package of the CLI, follows the CLI's release cycle, and the provider needs to own retries and error messages. Implement against the API's OpenAPI specification (`https://beta-api.livekit.cloud/v0/openapi`); where the live API differs from it, follow the live API and say so in a dated comment. Do not vendor the specification or generate code from it.
- The API is LiveKit's pre-GA `v0`. Before relying on an endpoint or field, check it against the live API, and record what was observed and when.
- Manage configuration, not content. Project settings, webhooks, API keys, members, SIP trunks, dispatch rules and phone numbers belong here; rooms, participants, egress, dispatches, invites and agent deployments do not.
- SIP objects are replaced whole by the API. Update reads the object, overwrites only the fields the resource models and replaces it, so unmodeled fields survive; never build a replace from the model alone. Never send the `********` password mask back.
- Never let a test buy a phone number or add a real user: acceptance tests for `livekit_phone_number` and `livekit_project_member` writes do not exist on purpose, and the fake's comment says which of its behaviour was not observed live.
- `livekit_project_settings` sends only the arguments the configuration sets, and its delete changes nothing. A new setting is Optional + Computed with `UseStateForUnknown`, so that leaving it out leaves it alone.
- An object whose ID or secret is stored elsewhere must never be replaced to apply a change that an update endpoint can make. Where the API offers no update (API keys), say so in the attribute description.
- Follow Terraform Plugin Framework plan/state consistency, import, and diagnostic conventions. Every resource needs a lifecycle test against the in-memory fake API (`internal/provider/fake_livekit_test.go`), and the fake must keep mirroring observed live behavior: when `TestAccAPIFacts` shows a difference, change the fake and its dated comment.
- Destructive operations stay guarded: `livekit_api_key` keeps `deletion_protection = true` by default. A resource must never adopt something it did not create: creates are not idempotent, so refuse and point to `terraform import`. The client never repeats a write after a network error.
- Never expose credentials in diagnostics, logs, example files, or URLs. Mark secrets `Sensitive`; they still persist in state. Never print a session token, including one read from the LiveKit CLI configuration. Test fixtures and examples use made-up IDs and `example.com` domains, never values from a real project.
- Keep commits atomic and commit completed, verified work frequently. Run `make test` (and `make test-tofu`) before each code commit, and `make generate` when schema, examples or templates change. Configuration syntax in examples and tests must work on Terraform 1.5.7, the latest Terraform and the latest OpenTofu.
- Do not claim live LiveKit verification from local fixtures. Real API tests require explicit opt-in (`TF_ACC`, `LIVEKIT_ACC_PROJECT_ID`, a session) and refuse a project whose name does not start with `terraform-acc`. They create and delete objects marked `tf-acc-*`, put back the settings they change, and never touch anything else.
- Follow the Solcreek Gandi provider's OpenTofu Registry release layout. Preserve published version tags and the registered Solcreek signing identity.
